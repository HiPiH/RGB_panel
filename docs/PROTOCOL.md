# Протокол потока кадров

Реализовано в спринте 3 и проверено на стенде.

## Решение

Кадры идут по UDP, одна датаграмма — один кадр. Выбор против TCP и gRPC
разобран в журнале спринтов: при потере пакета TCP останавливает поток до
ретрансмиссии, а это от 200 мс, то есть четыре подряд пропущенных кадра и
видимый затык. В UDP потерянный кадр просто пропускается, через 50 мс приходит
следующий. Так же устроены промышленные протоколы для таких панелей, DDP и
Art-Net.

## Формат датаграммы

Заголовок 10 байт, дальше пиксели по три байта в порядке R, G, B.

| Смещение | Размер | Поле | Значение |
| --- | --- | --- | --- |
| 0 | 2 | magic | `0x52 0x50`, ASCII `RP` |
| 2 | 1 | version | 1 |
| 3 | 1 | flags | бит 0 — последний пакет кадра, остальные зарезервированы |
| 4 | 2 | seq | номер кадра, big-endian, переполняется по кругу |
| 6 | 2 | offset | индекс первого пикселя в кадре, big-endian |
| 8 | 2 | count | число пикселей в пакете, big-endian |
| 10 | 3 × count | pixels | R, G, B на пиксель |

Для панели 16 × 16 весь кадр помещается в одну датаграмму:

| Величина | Значение |
| --- | --- |
| Пикселей в кадре | 256 |
| Данные пикселей | 768 байт |
| Датаграмма целиком | 778 байт |
| Поток при 20 кадрах/с | 15.6 КБ/с |

778 байт заметно меньше 1472, то есть фрагментации по IP нет. Поля `offset` и
`count` нужны на будущее: панель больше 480 пикселей в одну датаграмму уже не
влезет, и кадр придётся резать на части. Сборка кусков пока не сделана, кадр
принимается целиком, но формат её допускает.

Порядок пикселей — построчный слева направо, сверху вниз. Физическая раскладка
ленты, включая змейку, остаётся заботой платы и в протоколе не отражается.

Порт по умолчанию 4210, задаётся в `include/Config.h`.

## Поведение платы

Два режима, переключение автоматическое.

| Режим | Когда | Что показывает |
| --- | --- | --- |
| `Demo` | кадров нет | демо-последовательность спринта 1 |
| `Live` | кадры идут | последний принятый кадр |

Правила:

- первый корректный пакет переводит плату в `Live`;
- молчание дольше 2 с возвращает в `Demo`, демо стартует с начала цикла;
- за один проход `loop()` вычитываются все накопившиеся датаграммы, но не
  больше восьми, чтобы всплеск трафика не задержал вывод на панель;
- кадр со «старым» номером `seq` отбрасывается, сравнение кольцевое, чтобы
  переполнение счётчика не выглядело как откат назад;
- пауза в потоке сбрасывает фильтр номеров, иначе перезапущенный отправитель
  начинает нумерацию с нуля и панель замирает до тех пор, пока счётчик не
  догонит прежнее значение;
- пакет с чужим `magic`, версией, нулевым или слишком большим `count`
  отбрасывается молча, счётчик ошибок растёт.

Показ ограничен сверху: между двумя `FastLED.show()` не меньше 8 мс. Лента из
256 диодов физически не может обновляться быстрее 125 раз в секунду.

## Счётчики

Раз в секунду в лог печатается строка вида:

```
поток: 20 кадр/с  пакетов 20  старых 0  битых 0  сеть: подключено 192.168.1.127
```

Значения: показано кадров за секунду, принято датаграмм, отброшено как
устаревшие, отброшено как битые.

## Отправитель для проверки

```
python scripts/send_frames.py <IP платы>
python scripts/send_frames.py <IP платы> --seconds 0
python scripts/send_frames.py <IP платы> --face очки --seconds 20
python scripts/send_frames.py <IP платы> --fps 60 --pattern sweep
```

| Картинка | Что показывает |
| --- | --- |
| `smiley` | карусель смайликов, по умолчанию |
| `rainbow` | плывущая радуга |
| `sweep` | бегущая строка, на ней видны пропуски кадров |
| `checker` | шахматка, на ней заметно залипание картинки |

Параметр `--seconds` задаёт длительность прогона, ноль означает бесконечный.
По умолчанию он равен одному полному кругу карусели.

### Карусель смайликов

Девять лиц во всю панель, каждое показывается 10 секунд, после последнего круг
начинается заново, то есть полный круг длится 90 секунд. Рисование и анимация лежат в `scripts/faces.py`, показать
одно лицо без карусели можно ключом `--face`.

| Смайлик | Что делает |
| --- | --- |
| улыбка | улыбается и время от времени моргает, улыбка то шире, то уже |
| глаза | два больших глаза во всю панель без лица, смотрят влево, прямо, вправо и моргают |
| подмигивание | подмигивает правым глазом, ухмылка съезжает вбок |
| хохот | глаза дугами вверх, рот открывается толчками, видны зубы и язык |
| удивление | круглые глаза, рот буквой «о», щёки то разгораются, то гаснут |
| поцелуй | губы трубочкой, сердечки улетают вправо и вверх |
| очки | тёмные очки, по стёклам пробегает блик |
| влюблён | сердечки вместо глаз бьются, улыбка меняется в такт |
| слёзы | глаза дугами вниз, скорбный рот, слёзы капают по очереди |

Анимация считается от прошедшего времени, а не от номера кадра, поэтому на
любой частоте выглядит одинаково.

Объём набирается тремя приёмами. Голова считается как освещённый шар: в каждом
пикселе берётся нормаль сферы, по ней диффузная составляющая и блик, свет падает
сверху слева. Края всех фигур сглаживаются по доле пикселя, попавшей внутрь, —
отсюда полутона вместо лесенки, а дробные координаты позволяют глазам моргать и
рту открываться плавно, а не рывком через целый пиксель. Черты лица красятся с
оглядкой на освещённость в этой точке, поэтому на теневой стороне они темнее.

Черты лица при этом не сглаживаются в полутон полностью: ядро мазка кладётся
в полную силу, и только его края уходят в прозрачность.

Картинка «глаза» стоит отдельно: это два больших глаза во всю панель, без
головы и рта. Белок семь пикселей в ширину и девять в высоту, внутри радужка,
зрачок и блик, радужка обрезается по белку. Зрачок и его строка выровнены по
сетке пикселей: на дробной координате он расплывался в серое пятно, сквозь
которое просвечивал белок. Закрытый глаз рисуется линией века в тусклом тёплом
цвете, а не чернотой, иначе на моргании панель выглядит просто погасшей. Без этого тонкая линия
рта расходилась на два полупрозрачных пикселя, и лицо выглядело выцветшим.
Рот, глаза и очки покрашены почти чёрным, а свет спадает по гамме 1.7, поэтому
тень глубокая, а лицо в целом остаётся ярким.

За круг карусели получается около 3600 разных цветов против 12 у плоского
варианта. Отрисовка кадра занимает 0.9 мс при бюджете 50 мс на 20 кадрах
в секунду.

Полутона видны тем лучше, чем выше яркость панели. Сейчас в прошивке стоит 40 из
255, и это упирается не в код, а в блок питания: выше начнёт срабатывать лимит
тока FastLED и яркость кадра поплывёт. С более мощным блоком поднимайте
`DEFAULT_BRIGHTNESS` и `POWER_SUPPLY_MILLIAMPS` вместе.

## Измерено на стенде

Панель 16 × 16 на WS2812B, ESP32 DevKit, точка доступа в той же комнате,
RSSI около −45 дБм.

| Проверка | Результат |
| --- | --- |
| 20 кадров/с, 60 с | отправлено 1200, принято 1200, потерь нет |
| 60 кадров/с, 12 с | принято 60 датаграмм в секунду, показано 60 кадров |
| Устаревшие и битые кадры | отброшены, счётчики растут, перезагрузок нет |
| Возврат к демо | через 2 с после остановки отправителя |
| Время от включения до сети | 8.3 с |
| Занято RAM и флеша | 14.7 % и 51.3 % |

Запас по частоте тройной: узкое место не сеть, а сама лента, которой на 256
диодов нужно 7.7 мс на кадр.

## Известные риски

**Драйвер RMT против Wi-Fi.** У исходного ESP32 в RMT нет DMA, буфер
дозаполняется по прерываниям, а прерывания Wi-Fi их задерживают. На 20 и 60
кадрах в секунду артефактов не замечено, но если они появятся при длительной
работе, вывод переводится на драйвер I2S флагом `FASTLED_ESP32_I2S`.

**Очередь приёма в lwIP.** Она короткая, и при всплеске отправитель просто
потеряет пакеты. Это ожидаемо и должно быть видно в счётчиках.

**Яркость.** Кадр из белых пикселей упирается в лимит питания, и FastLED
приглушит его целиком. На стенде это выглядит как просадка яркости всего кадра,
а не как ошибка.
