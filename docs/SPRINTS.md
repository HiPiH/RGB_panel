## Спринт 1 — демонстрационный стенд

**Статус:** завершён, 2026-09-07

**Цель.** После подачи питания панель целиком плавно проходит цвета от
чёрного к белому через весь остальной спектр. Задержка между соседними
цветами настраивается.

### Задачи

- [x] Каркас проекта PlatformIO под ESP32, зависимость FastLED
- [x] Вынести параметры железа в один заголовок `include/Config.h`
- [x] Класс `DemoSequence` — расчёт цвета демо-последовательности
- [x] Заливка панели и главный цикл в `src/main.cpp`
- [x] Документация по железу и питанию
- [x] Проверка сборки: `pio run` проходит, RAM 7.1 %, Flash 28.5 %

### Решения по ходу работы

**Маршрут цвета.** «От чёрного к белому через все цвета» разложен в четыре
участка по 256 шагов плюс пауза на белом: разгорание красного из темноты,
полный оборот по цветовому кругу, выцветание в белый, гашение до чёрного.
Гашение в конце добавлено, чтобы демо зацикливалось без рывка. Полный цикл —
1088 шагов, при шаге 20 мс это около 22 секунд.

**Цветовая модель.** Считаем в HSV и отдаём FastLED, который переводит в RGB.
В RGB те же переходы пришлось бы задавать вручную и они выглядели бы
неравномерно по яркости.

**Настраиваемая задержка.** Задержка задаётся не только константой
`DEMO_STEP_DELAY_MS`, но и методом `setStepDelayMs()` в рантайме. Это готовая
точка входа для спринта с удалённым управлением.

### Проблемы и как решены

**Питание.** 256 диодов на белом при полной яркости просят около 15 А, столько
блок питания стенда не даст, а просадка напряжения ломает передачу данных.
Решение: стартовая яркость 40 из 255 плюс `setMaxPowerInVoltsAndMilliamps(5,
2000)` — FastLED сам приглушает кадр, если тот не влезает в бюджет.
Подробности в [HARDWARE.md](HARDWARE.md).

**Блокирующая задержка.** Очевидный вариант с `delay()` в `loop()` пришлось бы
выбрасывать уже в следующем спринте, когда появятся Wi-Fi и обработка команд.
Сразу сделано на `millis()`, причём `update()` догоняет расписание циклом:
после долгой блокирующей операции демо не отстаёт, а перескакивает вперёд.

**Нулевая задержка.** При `stepDelayMs == 0` цикл догона в `update()` стал бы
бесконечным. `setStepDelayMs()` поднимает ноль до 1 мс.

**Выбор пина.** GPIO 13 вместо популярного GPIO 5: пятый — strapping-пин,
уровень на нём в момент сброса влияет на режим загрузки.

### Результат

`pio run` собирается без ошибок и предупреждений. Прошивка на железе ещё не
проверена — это первое, что нужно сделать в начале следующего спринта.

## Спринт 2 — подключение к Wi-Fi

**Статус:** завершён, 2026-09-08

**Цель.** Плата подключается к точке доступа. Имя сети и пароль лежат в файле
`.env`, который не попадает в git и не упоминается в исходниках.

### Задачи

- [x] `scripts/load_env.py` — перенос параметров из `.env` в прошивку на сборке
- [x] `.env` и `.env.example`, `.env` закрыт от git
- [x] Класс `WiFiLink` — неблокирующее подключение и переподключение
- [x] Состояние сети в секундном логе стенда
- [x] `docs/WIFI.md` — формат `.env`, поведение автомата, диагностика
- [x] Проверка сборки: `pio run` проходит, RAM 14.0 %, Flash 50.6 %

### Решения по ходу работы

**Неблокирующее подключение.** `WiFiLink` — автомат из четырёх состояний
(`Disabled`, `Connecting`, `Connected`, `Waiting`), продвигается вызовом
`update()` из `loop()`. Обычный `while (WiFi.status() != WL_CONNECTED) delay()`
остановил бы анимацию на всё время подключения, а при недоступной сети — навсегда.

**Свой реконнект вместо штатного.** `setAutoReconnect(false)`: иначе повторами
управляли бы два механизма сразу, и логика в логе стала бы нечитаемой.
`persistent(false)` — учётки не пишутся во флеш, они и так вшиты в прошивку.

**Пустой SSID не ломает сборку.** Если `.env` нет или он пуст, макросы
становятся пустыми строками, автомат стартует в `Disabled`, прошивка пишет об
этом в лог и работает как стенд. Проект собирается на любой машине без `.env`.

### Проблемы и как решены

**Экранирование пароля.** Первый вариант передавал значения флагами
`-DWIFI_SSID=...`. На проверке с тестовым паролем `p$ss"word\` выяснилось, что
пробел в имени сети рвёт аргумент командной строки на два, а `$` съедается
подстановкой SCons — до прошивки доезжал испорченный пароль, причём молча.
Решение: скрипт генерирует `include/WiFiCredentials.h` с двумя `#define`, где
достаточно экранирования по правилам C. Проверено сквозной сборкой копии
проекта с таким паролем — значения доезжают дословно.

**Полная пересборка на каждый запуск.** Скрипт перезаписывал заголовок всегда,
из-за чего менялась его дата и пересобирался весь проект. Теперь файл пишется
только при реальном изменении значений.

**Кракозябры в выводе сборки.** Консоль PlatformIO на Windows не в UTF-8,
русские сообщения скрипта превращались в мусор. Сообщения самого скрипта
переведены на ASCII, комментарии в коде остались русскими.

**Место во флеше.** С Wi-Fi прошивка заняла 76 % стандартного раздела в 1.3 МБ,
а впереди веб-интерфейс и OTA. Перешли на `min_spiffs.csv`: 1.9 МБ под
приложение, OTA сохраняется, занято стало 50.6 %. Смена таблицы разделов
требует полной перепрошивки платы, не только заливки приложения.

**Прошивка из перенаправленного вывода.** `pio run -t upload` падает с
`UnicodeEncodeError`, если вывод уходит в файл или в конвейер: прогресс-бар
esptool рисуется псевдографикой, а Python в этом случае берёт кодировку
консоли cp1251. Заливка обрывается на середине, а процесс esptool остаётся
висеть и держать COM-порт. Лечится переменной `PYTHONIOENCODING=utf-8`; если
обрыв уже случился, зависшие процессы python и esptool надо снять вручную.

### Результат

`pio run` собирается без ошибок. Плата прошита и проверена на железе 2026-09-09: демо
идёт, лог печатает шаг и цвет. Подключение к сети ещё не проверялось, потому
что `.env` на момент прошивки был пуст и автомат стартовал в `Disabled`.
Проверка сети остаётся первым пунктом следующего спринта.
