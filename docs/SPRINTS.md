# Журнал спринтов

Каждый спринт — одна законченная функциональность, в конце спринта коммит.
Формат записи: цель, задачи, проблемы и решения, результат.

---

## Спринт 1 — демонстрационный стенд

**Статус:** завершён, 2026-09-07

**Цель.** После подачи питания панель целиком плавно проходит цвета от
чёрного к белому через весь остальной спектр. Задержка между соседними
цветами настраивается.

### Задачи

- [x] Каркас проекта PlatformIO под ESP32, зависимость FastLED
- [x] Вынести параметры железа в один заголовок `include/Config.h`
- [x] Класс `DemoSequence` — расчёт цвета демо-последовательности
- [x] Заливка панели и главный цикл в `src/main.cpp`
- [x] Документация по железу и питанию
- [x] Проверка сборки: `pio run` проходит, RAM 7.1 %, Flash 28.5 %

### Решения по ходу работы

**Маршрут цвета.** «От чёрного к белому через все цвета» разложен в четыре
участка по 256 шагов плюс пауза на белом: разгорание красного из темноты,
полный оборот по цветовому кругу, выцветание в белый, гашение до чёрного.
Гашение в конце добавлено, чтобы демо зацикливалось без рывка. Полный цикл —
1088 шагов, при шаге 20 мс это около 22 секунд.

**Цветовая модель.** Считаем в HSV и отдаём FastLED, который переводит в RGB.
В RGB те же переходы пришлось бы задавать вручную и они выглядели бы
неравномерно по яркости.

**Настраиваемая задержка.** Задержка задаётся не только константой
`DEMO_STEP_DELAY_MS`, но и методом `setStepDelayMs()` в рантайме. Это готовая
точка входа для спринта с удалённым управлением.

### Проблемы и как решены

**Питание.** 256 диодов на белом при полной яркости просят около 15 А, столько
блок питания стенда не даст, а просадка напряжения ломает передачу данных.
Решение: стартовая яркость 40 из 255 плюс `setMaxPowerInVoltsAndMilliamps(5,
2000)` — FastLED сам приглушает кадр, если тот не влезает в бюджет.
Подробности в [HARDWARE.md](HARDWARE.md).

**Блокирующая задержка.** Очевидный вариант с `delay()` в `loop()` пришлось бы
выбрасывать уже в следующем спринте, когда появятся Wi-Fi и обработка команд.
Сразу сделано на `millis()`, причём `update()` догоняет расписание циклом:
после долгой блокирующей операции демо не отстаёт, а перескакивает вперёд.

**Нулевая задержка.** При `stepDelayMs == 0` цикл догона в `update()` стал бы
бесконечным. `setStepDelayMs()` поднимает ноль до 1 мс.

**Выбор пина.** GPIO 13 вместо популярного GPIO 5: пятый — strapping-пин,
уровень на нём в момент сброса влияет на режим загрузки.

### Результат

`pio run` собирается без ошибок и предупреждений. Прошивка на железе ещё не
проверена — это первое, что нужно сделать в начале следующего спринта.

## Спринт 2 — подключение к Wi-Fi

**Статус:** завершён, 2026-09-08

**Цель.** Плата подключается к точке доступа. Имя сети и пароль лежат в файле
`.env`, который не попадает в git и не упоминается в исходниках.

### Задачи

- [x] `scripts/load_env.py` — перенос параметров из `.env` в прошивку на сборке
- [x] `.env` и `.env.example`, `.env` закрыт от git
- [x] Класс `WiFiLink` — неблокирующее подключение и переподключение
- [x] Состояние сети в секундном логе стенда
- [x] `docs/WIFI.md` — формат `.env`, поведение автомата, диагностика
- [x] Проверка сборки: `pio run` проходит, RAM 14.0 %, Flash 50.6 %

### Решения по ходу работы

**Неблокирующее подключение.** `WiFiLink` — автомат из четырёх состояний
(`Disabled`, `Connecting`, `Connected`, `Waiting`), продвигается вызовом
`update()` из `loop()`. Обычный `while (WiFi.status() != WL_CONNECTED) delay()`
остановил бы анимацию на всё время подключения, а при недоступной сети — навсегда.

**Свой реконнект вместо штатного.** `setAutoReconnect(false)`: иначе повторами
управляли бы два механизма сразу, и логика в логе стала бы нечитаемой.
`persistent(false)` — учётки не пишутся во флеш, они и так вшиты в прошивку.

**Пустой SSID не ломает сборку.** Если `.env` нет или он пуст, макросы
становятся пустыми строками, автомат стартует в `Disabled`, прошивка пишет об
этом в лог и работает как стенд. Проект собирается на любой машине без `.env`.

### Проблемы и как решены

**Экранирование пароля.** Первый вариант передавал значения флагами
`-DWIFI_SSID=...`. На проверке с тестовым паролем `p$ss"word\` выяснилось, что
пробел в имени сети рвёт аргумент командной строки на два, а `$` съедается
подстановкой SCons — до прошивки доезжал испорченный пароль, причём молча.
Решение: скрипт генерирует `include/WiFiCredentials.h` с двумя `#define`, где
достаточно экранирования по правилам C. Проверено сквозной сборкой копии
проекта с таким паролем — значения доезжают дословно.

**Полная пересборка на каждый запуск.** Скрипт перезаписывал заголовок всегда,
из-за чего менялась его дата и пересобирался весь проект. Теперь файл пишется
только при реальном изменении значений.

**Кракозябры в выводе сборки.** Консоль PlatformIO на Windows не в UTF-8,
русские сообщения скрипта превращались в мусор. Сообщения самого скрипта
переведены на ASCII, комментарии в коде остались русскими.

**Место во флеше.** С Wi-Fi прошивка заняла 76 % стандартного раздела в 1.3 МБ,
а впереди веб-интерфейс и OTA. Перешли на `min_spiffs.csv`: 1.9 МБ под
приложение, OTA сохраняется, занято стало 50.6 %. Смена таблицы разделов
требует полной перепрошивки платы, не только заливки приложения.

**Прошивка из перенаправленного вывода.** `pio run -t upload` падает с
`UnicodeEncodeError`, если вывод уходит в файл или в конвейер: прогресс-бар
esptool рисуется псевдографикой, а Python в этом случае берёт кодировку
консоли cp1251. Заливка обрывается на середине, а процесс esptool остаётся
висеть и держать COM-порт. Лечится переменной `PYTHONIOENCODING=utf-8`; если
обрыв уже случился, зависшие процессы python и esptool надо снять вручную.

### Результат

`pio run` собирается без ошибок. Плата прошита и проверена на железе 2026-09-09: демо
идёт, лог печатает шаг и цвет. Подключение к сети ещё не проверялось, потому
что `.env` на момент прошивки был пуст и автомат стартовал в `Disabled`.
Проверка сети остаётся первым пунктом следующего спринта.

## Спринт 3 — поток кадров по UDP

**Статус:** завершён, 2026-09-09

**Цель.** Пока кадров нет, панель играет демо. Как только приходит поток,
показывает присланные кадры 16 × 16 с частотой не ниже 20 в секунду.

### Задачи

- [x] `include/FrameProtocol.h` — разбор заголовка чистыми функциями
- [x] `FrameReceiver` — сокет, приём, фильтр номеров, счётчики
- [x] Переключение режимов «демо» и «поток» в `main.cpp`
- [x] `scripts/send_frames.py` — отправитель с пробными картинками,
      по умолчанию смайлик с циклом анимации в 10 секунд
- [x] Статистика раз в секунду в лог
- [x] Приёмка на железе: 1200 кадров за 60 с, потерь нет

### Решения по ходу работы

**Приём пишет прямо в буфер панели.** Отдельный буфер кадра стоил бы ещё 768
байт и лишнего копирования, а выигрыша не давал: пока кадр не показан, старый
всё равно не нужен.

**Не больше восьми датаграмм за проход.** Иначе всплеск трафика откладывал бы
вывод на панель на неопределённое время.

**Вывод не чаще одного раза в 8 мс.** Лента из 256 диодов физически не
обновляется быстрее 125 раз в секунду, всё сверх этого — потраченный процессор.

### Проблемы и как решены

**Панель замирала после перезапуска отправителя.** Нашлось тестом на фильтр
номеров. Отправитель начинает нумерацию с нуля, а плата помнит прежний номер и
считает новые кадры устаревшими. При номере 400 панель молчала бы 20 секунд.
Решение: пауза в потоке дольше таймаута сбрасывает фильтр, следующий пакет
принимается с любым номером.

**Первая попытка подключения к Wi-Fi всегда пропадала.** Плата выходила в сеть
только со второй попытки, через 22 с после включения. Проверено, что дело не в
`disconnect` перед `begin` и не в паузе на подъём радиомодуля: с ними ничего не
изменилось, помогает именно повторный вызов `begin`, то есть первую ассоциацию
теряет точка доступа. Раз повтор дешевле ожидания, первая попытка теперь
обрывается через 4 с, а пауза перед повтором сокращена до 2 с. Время до сети
упало с 22.3 с до 8.3 с.

**Сон модема.** `WiFi.setSleep(false)` перенесён из `begin` в момент
установленного соединения: настройка ложится на поднятое соединение, а не на
ещё не существующее.

**Монитор порта мешал сам себе.** `pio device monitor` при перенаправлении
вывода то буферизует его целиком, то оставляет осиротевшие процессы python,
которые держат COM-порт, и следующий запуск падает с отказом в доступе. Для
автоматических проверок порт теперь читается напрямую через pyserial, причём
DTR и RTS перед открытием сбрасываются в ноль: иначе плата остаётся в сбросе и
молчит.

**Устаревший вызов.** `WiFiUDP::flush()` в этой версии ядра помечен устаревшим,
заменён на `clear()`.

### Результат

Проверено на железе 2026-09-09. Минутный прогон на 20 кадрах в секунду: 1200
отправлено, 1200 принято, ни одного устаревшего или битого кадра, перезагрузок
нет. На 60 кадрах в секунду плата держит поток так же уверенно. Семь заведомо
битых датаграмм отброшены со счётчиком ошибок и без перезагрузки. После
остановки отправителя панель возвращается к демо за 2 с. Цифры и формат
датаграммы в [PROTOCOL.md](PROTOCOL.md).

## Спринт 4 — обновление по воздуху

**Статус:** завершён, 2026-09-09

**Цель.** Заливать прошивку по сети, без USB-кабеля.

### Задачи

- [x] `OtaUpdater` — приём обновления и полоса прогресса на панели
- [x] Пароль `OTA_PASSWORD` из `.env` тем же путём, что и параметры сети
- [x] Окружение `esp32dev-ota` с протоколом `espota`, пароль подставляется сам
- [x] `docs/OTA.md` — команды, поведение панели, диагностика
- [x] Проверка на железе: прошивка залита по сети и плата ожила

### Решения по ходу работы

**Пустой пароль выключает OTA, а не отключает проверку.** Открытая заливка в
локальной сети означала бы, что любой в этой сети может залить в панель что
угодно. Поэтому при пустом `OTA_PASSWORD` обновление не запускается, и плата
пишет об этом в лог.

**Прогресс показывает сама панель.** Экрана у стенда нет, а заливка идёт около
минуты, и без индикации непонятно, работает она или повисла. Панель гаснет на
старте, синяя полоса растёт по проценту записанного, зелёная заливка означает
успех, красная — сбой. Полоса перерисовывается только на смене процента: вывод
на ленту стоит 7.7 мс, на каждом пакете заливки это тормозило бы обновление.

**Пароль не попадает ни в git, ни в `platformio.ini`.** Его добавляет в
командную строку отдельный скрипт `scripts/ota_auth.py`.

### Проблемы и как решены

**Первую прошивку всё равно надо залить по кабелю.** OTA не спасает саму себя:
чтобы плата начала принимать обновления, прошивка с этим кодом должна на ней
оказаться. Так что зависимость от USB снимается не сразу, а после первой
удачной заливки.

**Пароль терялся по дороге к espota.** Первая заливка упала с
`Authentication Failed`, причём пароль в `.env` и в прошивке совпадал побайтно.
В отладочном выводе espota оказалось `auth=''`. Причина в порядке выполнения:
подстановка пароля жила в pre-скрипте, а платформа задаёт флаги espota через
`env.Replace` уже после pre-скриптов и стирает всё, что добавлено раньше.
Подстановка вынесена в отдельный post-скрипт `scripts/ota_auth.py`.

**USB перестал работать после смены блока питания.** Порт COM5 то пропадает
из системы совсем, то появляется и не открывается с ошибкой «устройство не
работает». При этом сама плата в полном порядке: отвечает по сети без потерь,
не перезагружается. То есть страдает только канал USB, а не питание платы.
Вероятные причины по убыванию: внешние 5 В заведены на пин платы и подпирают
линию USB, обратный ток панели течёт через землю USB, плохой кабель. Из-за
этого спринт и остался непроверенным, и из-за этого же OTA вообще появилась
в плане раньше времени.

### Результат

Проверено на железе 2026-09-09. Прошивка залита по кабелю, затем та же прошивка
успешно залита по сети: аутентификация принята, запись заняла 18 с, плата
поднялась и вернулась в сеть. После обновления карусель шла 45 с на 20 кадрах
в секунду, принято 887 датаграмм из 900 отправленных, устаревших и битых нет,
перезагрузок нет. Расхождение в 13 кадров приходится на края окна: счётчики
платы и отправитель не выровнены по границам секунд.

Заняло: RAM 15.9 %, флеш 53.5 %, прирост от `ArduinoOTA` и mDNS составил 44 КБ.
Кабель для заливки больше не нужен.

### Почему UDP, а не gRPC

Считали 2026-09-09 по запросу на gRPC-сервер с потоком кадров 16 × 16 и
частотой не ниже 20 в секунду.

По трафику задача решается с запасом в обоих вариантах: кадр весит 768 байт
пикселей, при 20 кадрах в секунду это около 16 КБ/с, то есть 5 % даже от
пессимистичной оценки TCP на ESP32. По времени вывод 256 диодов занимает 7.7 мс
из 50 мс бюджета, запас четырёхкратный.

Против gRPC сыграли три вещи. Готового сервера для ESP32 нет: пришлось бы
уходить с Arduino на ESP-IDF и собирать связку nghttp2 и nanopb вручную, это два
или три спринта. С TLS запас по куче становится некомфортным, потому что nghttp2
и mbedTLS вместе просят до 110 КБ из примерно 200 КБ свободных. И главное, TCP
на потере пакета останавливает поток до ретрансмиссии, а это от 200 мс и четыре
подряд пропущенных кадра.

UDP снимает всё три пункта: кадр помещается в одну датаграмму без фрагментации,
потеря кадра незаметна, кода в разы меньше.
